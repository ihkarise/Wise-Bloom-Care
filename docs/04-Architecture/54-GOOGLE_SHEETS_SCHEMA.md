## 1. Purpose

Defines the concrete v1 storage layout in Google Sheets: how the storage-neutral data model (`55`) is realised as sheet tabs ("tables"), the columns, keys, indexing approach, and integrity rules the adapter enforces (since Sheets provides none). This is a v1 implementation detail behind the adapter and is expected to be superseded by a relational store.

## 2. Scope

Sheet-as-table layout, key/index strategy, and adapter-enforced integrity for v1. Field-level types/validation: `docs/05-Data/72`, `73`. Storage-neutral model: `55`.

## 3. Modelling Approach

- One **spreadsheet** per environment (dev/staging/prod), private.
- One **tab = one table**; row 1 = header (column names); each subsequent row = one record.
- Keys are app-generated **UUIDs**; foreign keys are UUID references (adapter-enforced, not DB-enforced).
- Append-only tables for events; versioned updates for correctable records (`docs/05-Data/77`).
- Lightweight **index tabs** for hot lookups (e.g., events by family) to reduce scans.

## 5. Keys, Indexes & Integrity (adapter-enforced)

- **PKs:** UUIDs generated by the adapter; uniqueness enforced by the adapter on insert.
- **FKs:** UUID references; the adapter validates existence on write (no DB constraint exists).
- **Immutable link:** `child_records.mother_id` is written once by DeliveryService and never updated (Vision BR-V2).
- **Append-only:** `events` and `audit_log` are never updated/deleted in place; corrections are new rows (`77`).
- **Indexing:** index tabs (e.g., `idx_events_by_family`) maintained on write for hot queries; kept consistent under `LockService` (`53`).
- **Uniqueness rules:** e.g., one active session per token; enforced by adapter.

## 6. Storage Media (files) 

- Report/journal media (PDFs, images, ultrasound) are stored in **private Google Drive**, referenced by `file_ref` in the relevant table; access mediated by the backend (never public links) (`docs/09-Security/123`).

## 7. Consistency & Concurrency

- No transactions in Sheets → adapter uses `LockService` for multi-row/index-affecting writes, append-only patterns, and idempotency keys (`53` §7).
- Reads may be eventually consistent w.r.t. indexes; critical reads re-validate.

## 8. Business Rules

- BR-1: Only the adapter reads/writes these tabs (`52` BR-1).
- BR-2: `child_records.mother_id` is immutable post-creation.
- BR-3: `events`/`audit_log` are append-only.
- BR-4: FKs validated by the adapter on write; orphan references rejected.
- BR-5: Media stored privately in Drive, referenced only; no public links.

## 9. Edge Cases

- Row/scale limits of Sheets (cell/row caps) → monitor; migrate adapter when approached (RSK-9).
- Concurrent index updates → `LockService`.
- Manual spreadsheet tampering → mitigated by restricted access + audit; app treats Sheets as private backend, not user-editable.
- Large media → Drive, not cells.
