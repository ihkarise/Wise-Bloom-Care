## 1. Purpose
Describes the V3 horizon — "Ecosystem" — opening the platform to clinicians, working offline, integrating devices, and expanding across jurisdictions/languages. V3 depends on validating the storage-migration boundary at scale.

## 2. Scope
V3 themes and entry gates. Architecture is designed to accommodate these without redesign (`docs/04-Architecture/50`).

## 3. V3 Capabilities
- **Clinician / doctor portal:** scoped, RBAC-controlled read + structured contribution (`docs/09-Security/123` future role); provenance-rich.
- **Offline-first PWA:** offline capture + conflict-safe sync via the same API contract (`docs/04-Architecture/51`, `56`).
- **Device/wearable integration:** BP/glucose/activity ingestion (validated, user-reviewed).
- **Storage migration:** backend adapter swapped to Postgres/Supabase/Firebase/Cloud SQL with 0 frontend contract changes (`docs/04-Architecture/52`).
- **Localisation:** multi-language/multi-jurisdiction (schedules, disclaimers, emergency numbers).

## 4. Entry Gates
- **Storage migration validated** (MS-3.1: backend swap, 0 frontend contract changes) before ecosystem scale.
- Offline data-integrity + conflict resolution proven.
- Clinician-role RBAC + provenance in place.
- Jurisdiction/legal readiness for new markets (`docs/09-Security/126`).

## 5. Business Rules
- BR-1 V3 uses the existing API contract; storage/runtime changes don't alter it (NFR-6).
- BR-2 Clinician access is strictly RBAC-scoped, provenance-tracked, audited.
- BR-3 Offline sync preserves continuity invariants (no duplicate/orphan; append-only).
- BR-4 Localisation adapts schedules/disclaimers/emergencies per jurisdiction.
